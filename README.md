# godot-mcp

MCP-сервер для Godot 4.x. Даёт агенту читать и править файлы проекта, проверять GDScript, собирать сцены средствами самого движка и запускать игру с разбором ошибок.

## Сборка

Требуется Go 1.25+ (этого требует официальный `github.com/modelcontextprotocol/go-sdk`).

```sh
go mod tidy
make build            # -> bin/godot-mcp
make test             # юнит-тесты
make test-godot       # интеграционные тесты с настоящим движком (GODOT_BIN)
# тесты godot_run_tests дополнительно нужны GUT_ADDON_DIR=.../addons/gut
# и GDUNIT4_ADDON_DIR=.../addons/gdUnit4 — без них они пропускаются
```

## Подключение к клиенту

Claude Desktop / Claude Code (`.mcp.json` или `claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "godot": {
      "command": "/path/to/bin/godot-mcp",
      "args": ["--project", "/path/to/my-game", "--root", "/path/to/games"],
      "env": { "GODOT_BIN": "/Applications/Godot.app/Contents/MacOS/Godot" }
    }
  }
}
```

Все аргументы необязательны:

- `--project` — проект, активный сразу после запуска. Без него агент выбирает проект сам через `godot_select_project`.
- `--root` (можно несколько раз, или `GODOT_MCP_ROOTS` через `:`) — открывать проекты только из этих каталогов; они же просматриваются в `godot_list_projects`. Без `--root` можно открыть любой каталог с `project.godot`.

Бинарник Godot ищется так: `--godot` → `$GODOT_BIN` → `godot`/`godot4` в PATH → `/Applications/Godot.app`.

`--lsp=off` (или `GODOT_MCP_LSP=off`) отключает фоновый редактор для проверки скриптов — см. ниже.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `godot_list_projects` | проекты для выбора: открытые в сессии, из менеджера проектов Godot (избранные выше), найденные в `--root` |
| `godot_select_project` | сделать проект активным |
| `godot_project_info` | имя, главная сцена, фичи движка, autoload'ы, действия ввода |
| `godot_class_docs` | справка по API установленной версии движка: классы, встроенные типы, глобальные функции; распознаёт имена из Godot 3 |
| `godot_list_files` | листинг проекта (без `.godot/`, `*.import`, `*.uid`) |
| `godot_read_file` | чтение текстового файла, опционально диапазон строк |
| `godot_write_file` | атомарная запись файла |
| `godot_edit_file` | замена уникального фрагмента (в стиле str_replace) |
| `godot_check_script` | проверка `.gd` через языковой сервер фонового редактора (или `--check-only`), ошибки и предупреждения с файлом и строкой |
| `godot_symbol_info` | что за символ в скрипте: сигнатура и doc-комментарий, где объявлен, все использования по проекту |
| `godot_find_symbol` | где в скриптах проекта объявлены функции, переменные, сигналы, классы; структура одного файла |
| `godot_import` | headless-импорт ассетов и обновление кеша `class_name` |
| `godot_create_scene` | сборка `.tscn` из JSON-дерева узлов через `PackedScene` + `ResourceSaver`, со встроенными подресурсами и сигналами |
| `godot_scene_tree` | сцена в JSON в том же формате, что принимает `godot_create_scene`: узлы, изменённые свойства, инстансы, соединения |
| `godot_edit_scene` | атомарная правка существующей сцены списком операций с сохранением UID |
| `godot_run_script` | одноразовый GDScript (`extends SceneTree`) внутри проекта |
| `godot_run_project` | запуск игры или сцены в фоне, возвращает `run_id` и первые секунды вывода |
| `godot_get_output` | новый вывод по курсору `since`, long-poll, разобранные ошибки |
| `godot_screenshot` | снимки выбранных кадров игры (`--write-movie`) плюс ошибки за это время |
| `godot_run_tests` | тесты GUT или gdUnit4 со сводкой и упавшими тестами (файл, строка, сообщение) |
| `godot_game_tree` | живое дерево сцены запущенной игры со значениями нужных свойств |
| `godot_game_eval` | выражение Godot внутри игры: прочитать состояние или вызвать метод |
| `godot_game_set` | изменить свойства узла в запущенной игре |
| `godot_game_input` | имитация ввода: действия Input Map, клавиши, текст, мышь, паузы |
| `godot_game_screenshot` | снимок текущего кадра запущенной игры |
| `godot_stop_project` | SIGTERM → SIGKILL всей группы процессов |
| `godot_list_runs` | последние запуски и их статус |

### Встроенные подресурсы в `godot_create_scene`

Свойству-ресурсу можно передать не только путь `res://`, но и объект с ключом `_type`. Такой ресурс создаётся движком и сохраняется внутри `.tscn` как `sub_resource`:

```json
{"type": "CollisionShape2D", "name": "Shape", "properties": {
  "shape": {"_type": "RectangleShape2D", "size": "Vector2(32, 48)"}
}}
```

Остальные ключи объекта — свойства ресурса, по тем же правилам, что и у узлов, поэтому вложенность работает (`GradientTexture2D` → `Gradient`). В `_type` можно указать `class_name` пользовательского ресурса (после `godot_import`) или передать `"_script": "res://item.gd"`. Типизированные массивы вроде `Array[ItemData]` принимают списки таких объектов. Ошибки говорят, что ожидалось: `CollisionShape2D.shape: cannot assign Gradient, the property expects Shape2D`.

### Сигналы

Соединения задаются списком `connections` рядом с `root`, пути узлов — относительно корня сцены (`"."` — сам корень):

```json
"connections": [
  {"from": "UI/Start", "signal": "pressed", "to": ".", "method": "_on_start_pressed"},
  {"from": "Timer", "signal": "timeout", "to": ".", "method": "_on_timeout", "binds": ["tick"], "flags": 1}
]
```

Метод должен уже существовать в скрипте получателя. Узлы, сигнал, метод и число аргументов (аргументы сигнала + `binds` против обязательных и необязательных параметров метода) проверяются при сборке. Поэтому ошибка вроде `UI/Sound:toggled -> .:_on_start_pressed: the method takes 0 arguments, but the signal passes 1` приходит сразу, а не во время игры. `flags` — это `CONNECT_*`: 1 — отложенный вызов, 4 — однократный.

### Правка существующих сцен

`godot_scene_tree` читает сцену через `SceneState` — ровно то, что лежит в файле, — и отдаёт её в формате `godot_create_scene`, так что прочитанное дерево можно сразу пересобрать. У каждого узла есть `path` относительно корня. Слишком большие значения (например, данные тайлов) заменяются заглушкой `{"_omitted": ...}`, записать её обратно нельзя.

`godot_edit_scene` применяет операции по порядку: `add_node`, `remove_node`, `set_properties`, `rename`, `move`, `groups`, `connect`, `disconnect`. Если хоть одна не удалась, файл не меняется, а ошибка называет операцию: `operations[1] remove_node: no node at 'Nope'`. UID сцены, `unique_id` узлов и id внешних ресурсов сохраняются, поэтому diff содержит только сделанные изменения. Узлы внутри инстанцированной сцены здесь не правятся — ошибка подскажет, какую сцену открыть.

### Скриншоты

`godot_screenshot` запускает игру в режиме Movie Maker (`--write-movie` с `--fixed-fps`) и возвращает выбранные кадры как изображения. Время детерминировано: кадр N — это состояние игры ровно через N/fps секунд, так что одинаковый вызов даёт одинаковую картинку. Проект менять не нужно.

- По умолчанию снимается кадр 60 (1 с при 60 FPS); можно до 8 кадров за вызов, не дальше 3600-го.
- Картинки шире `max_width` (по умолчанию 1280) уменьшаются, чтобы не расходовать контекст агента.
- Вместе с кадрами приходят ошибки игры за это время; если игра вышла раньше, недоснятые кадры перечислены в `missing`.
- Нужно настоящее окно: в `--headless` нет рендера. На время записи (примерно столько же, сколько игрового времени) открывается окно игры. На Linux-сервере без дисплея запускайте MCP-сервер под `xvfb-run`.

### Тесты

`godot_run_tests` запускает GUT или gdUnit4 (фреймворк определяется по `addons/`) и разбирает их JUnit-отчёт: сводка и каждый упавший тест с файлом, строкой и сообщением. Если `class_name` фреймворка ещё не в кеше, сначала выполняется импорт.

- `load_errors` — тестовые скрипты, которые не скомпилировались. GUT такие файлы молча пропускает и выходит с кодом 0, а gdUnit4 не запускает вообще ничего; здесь это всегда считается провалом.
- `addon_errors` — ошибки внутри `addons/`, например версия фреймворка не под этот движок (GUT 9.7 рассчитан на Godot 4.7 и на 4.6 выдаёт ошибки разбора; для 4.6 подходит 9.6.x).
- Фильтр по имени теста (`test`) есть только у GUT; в gdUnit4 сужайте запуск путями к файлам.
- Отчёт пишется во временный каталог в `.godot/` и удаляется после разбора.

### Справка по API

`godot_class_docs` отвечает по API той версии Godot, что установлена, а не той, что помнит модель. Данные берутся у самого движка (`--dump-extension-api-with-docs` плюс `--doctool` для значений по умолчанию и `@GDScript`) один раз на версию и кешируются в каталоге кеша пользователя (`~/Library/Caches/godot-mcp/api` на macOS); первый вызов занимает пару секунд, следующие — мгновенны.

- `name` — обзор класса: цепочка наследования, описание, свойства с типами и значениями по умолчанию, методы с сигнатурами, сигналы, перечисления. Сеттеры и геттеры свойств не дублируются.
- `name` + `member` (или `"Class.member"`) — полное описание члена с примерами на GDScript; унаследованные члены ищутся по цепочке предков.
- `search` — поиск классов и членов по части имени.
- Имена из Godot 3 (`KinematicBody2D`, `instance()`, `yield`, `rect_size`...) распознаются и указывают на замену в Godot 4. Для `class_name` проекта подсказывается, в каком скрипте он объявлен.

### Работа с запущенной игрой

`godot_run_project` по умолчанию подключает к игре мост: небольшой автозагружаемый скрипт, через который работают инструменты `godot_game_*`. Проект при этом не меняется:

- скрипт моста кладётся в `.godot/` (служебный каталог, скрыт в редакторе и в git), а в `override.cfg` на время старта дописывается одна строка `[autoload]`. Godot читает этот файл поверх `project.godot`; как только игра подключилась, файл возвращается в исходное состояние (если он был — байт в байт, со всеми автозагрузками пользователя);
- игра подключается к серверу по TCP на `127.0.0.1` со случайным портом и токеном из переменной окружения. Без этой переменной мост ничего не делает, поэтому даже оставшийся после аварии `override.cfg` не влияет на запуск из редактора (а при следующем старте сервер его уберёт);
- мост работает и на паузе, и в `--headless` (кроме снимка экрана), и в проектах, где предупреждения GDScript — ошибки.

Типичный цикл: `godot_run_project` → `godot_game_input` (подержать «вправо» 0,5 с) → `godot_game_eval` (`position.x`, `is_on_floor()`) → поправить скрипт → перезапустить. `no_bridge: true` запускает игру без моста.

### Быстрая проверка скриптов

`godot_check_script` проверяет файлы через языковой сервер фонового редактора (`godot --editor --headless --lsp-port N`): несколько миллисекунд на файл вместо ~0,4 с на отдельный процесс `--check-only`. Ошибки те же, а вдобавок приходят предупреждения (`UNUSED_VARIABLE` и т.п.); `all_ok` зависит только от ошибок. Поле `via` показывает, каким путём шла проверка.

- Редактор запускается при первой проверке (~2 с, при первом открытии проекта дольше — он импортирует ассеты) и останавливается после 10 минут без проверок или вместе с сервером.
- Скрипты, изменённые на диске, перед каждой проверкой отправляются редактору, так что зависимые файлы видят новые типы и сигнатуры. Новый или удалённый `class_name` и изменения `project.godot` редактор без окна не подхватывает — тогда он перезапускается.
- Если редактор не запустился или не ответил, проверка идёт через `--check-only`, а причина пишется в `note`.
- Тот же фоновый редактор отвечает на вопросы о коде: `godot_symbol_info` (сигнатура, doc-комментарий `##`, переход к объявлению, все использования по проекту, в том числе в неоткрытых файлах) и `godot_find_symbol` (поиск объявлений по части имени и структура файла). Символ указывается по имени — с номером строки или без, тогда берётся первое вхождение. Упоминания в комментариях в список использований не попадают. Описания членов движка приходят на английском независимо от языка вашего редактора.
- Фоновый редактор работает с тем же проектом, что и ваш открытый редактор: как и `godot_import`, он может создать недостающие `.uid`-файлы и импортировать новые ассеты. Если это мешает, запустите сервер с `--lsp=off`.

### Несколько проектов

Сервер не привязан к одному проекту. `godot_list_projects` показывает, из чего выбирать: проекты, уже открытые в этой сессии, список менеджера проектов Godot (`projects.cfg` редактора, избранные — выше) и проекты в каталогах `--root`. `godot_select_project` делает проект активным.

Любой инструмент принимает необязательный `project` — путь к каталогу проекта (или к его `project.godot`, `~` раскрывается) — и работает с ним, не переключая активный. У каждого открытого проекта свои запуски игр, мост и фоновый редактор; `run_id` уникален во всех проектах, поэтому `godot_get_output`, `godot_stop_project` и `godot_game_*` находят проект по `run_id` сами. Справка `godot_class_docs` работает и без выбранного проекта.

## Безопасность

Файловые инструменты работают только внутри проекта; какие проекты можно открыть, ограничивает `--root`. Мост слушает только `127.0.0.1` и принимает одно подключение с токеном этого запуска. Запрещены абсолютные пути, `..`, симлинки наружу, а также `.godot/` и `.git/`. При этом `godot_run_script` и запуск игры исполняют произвольный код с правами пользователя. Это осознанный компромисс: для агента, который пишет игру, так работает любой запуск проекта.
